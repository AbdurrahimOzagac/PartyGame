# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ShooterParty: a 3–4 player online party game in Unity 6000.3.9f1 (URP, Input System, Netcode for GameObjects 2.13, Unity Transport 2.7.4). Cube critters with a spit shot play a playlist of mini-games; the first is Knockback Arena. The full docs are in `Assets/Ezel/ShooterParty/Docs/`: `ARCHITECTURE.md` (read it before changing core code), `ADDING_A_MINIGAME.md` and `SERVER_OPS.md`. `README.md` covers build, launch and tests for players and teammates.

## Layout

- `Assets/Ezel/ShooterParty/`: the core framework (assemblies `ShooterParty.Runtime`, `.Editor`, `.EditModeTests`, `.PlayModeTests`).
- `Assets/Ezel/KnockbackArena/`: the mini-game (`KnockbackArena.Runtime`, `.Editor`, `.Tests`), plus the **shared art kit** (critters, blob, fonts, sprites, VFX, audio). The art stays here because generators and Blender export paths point at it. Do not move or rename it.
- `Assets/Abd`, `Assets/Ardil`, `Assets/Kha`: teammates' folders. Leave them alone.
- `projects/shooterparty/`: design spec, plans, and `server/` (Python room service, systemd units, tunnel config, `deploy.sh`, `e2e_local.sh`). `projects/game_assets/` holds the Blender sources.

## Commands

Batch commands need the Unity editor closed on this project (it locks the project). Exit code 0 means success.

```sh
UNITY=/Applications/Unity/Hub/Editor/6000.3.9f1/Unity.app/Contents/MacOS/Unity

# Tests (EditMode = pure logic; PlayMode = a real NGO host)
"$UNITY" -batchmode -projectPath . -runTests -testPlatform EditMode -assemblyNames ShooterParty.EditModeTests -testResults "$PWD/Logs/editmode.xml" -logFile Logs/editmode.log
"$UNITY" -batchmode -projectPath . -runTests -testPlatform PlayMode -assemblyNames "ShooterParty.PlayModeTests;KnockbackArena.Tests" -testResults "$PWD/Logs/playmode.xml" -logFile Logs/playmode.log
# One test or fixture: add -testFilter, e.g. -testFilter ShooterParty.Tests.ScoreRulesTests (full name or regex;
# test namespaces are ShooterParty.Tests and KnockbackArena.Tests)

# Builds go to Builds/<target>/ (gitignored)
"$UNITY" -batchmode -nographics -quit -projectPath . -logFile - -executeMethod ShooterParty.EditorTools.PartyBuild.BatchMac
# also BatchWindows, BatchLinux, BatchPiServer (IL2CPP Linux Arm64, 5–15 min, needs ~4 GB free disk)

# Room service tests (Python 3, standard library only)
(cd projects/shooterparty/server/rooms && python3 -m unittest test_room_service test_tickets)
(cd projects/shooterparty/server && python3 -m unittest test_e2e_check)

# End to end: a dedicated server + 3 autopilot clients from one macOS build
# scenarios: basic, drop, drop-all, leave-during-load, rooms (~80 s each)
projects/shooterparty/server/e2e_local.sh basic Builds/macOS/ShooterParty.app/Contents/MacOS/406Party
```

`RoomServiceClientTests` is skipped without `python3` on the PATH; the `WssBridge` test in category `Online` needs internet.

In the editor, the game always starts from `Assets/Ezel/ShooterParty/Scenes/SP_Boot.unity`. **PRACTICE VS BOTS** (you + 3 bots, no network) is the default way to test a mini-game.

## Generated assets: change the builders, not the output

Scenes, prefabs, UI and data assets are generated by editor code. Hand edits are lost on the next rebuild.

- **ShooterParty > Rebuild core assets** (`ShooterPartySetup.BuildAll`): `UI_Root.prefab` (via `UiBuilder`, `LobbyBuilder`, `HudBuilder`, palette and helpers in `UiKit`), the `SP_Boot`/`SP_Menu`/`SP_Lobby` scenes, `MiniGameCatalog.asset` (finds every `MiniGameDefinition` under `Assets/Ezel`) and the network prefab list.
- **Knockback Arena > Rebuild Everything** (`ArenaSetup.RebuildEverything`): critters, VFX, UI widget, audio, the ice arena scene, then the core rebuild last.
- If two branches both regenerated core files, do not merge them by hand: take either side, then run Rebuild core assets again.

## Architecture essentials

- **Dependencies point one way:** mini-game → core. The core never references a mini-game; it finds them through `MiniGameCatalog`. A mini-game never references another mini-game's assembly. A new mini-game is its own folder, three asmdefs, a `MiniGameController` subclass, a scene with one `MiniGameScene` marker, and a `MiniGameDefinition` asset (`ADDING_A_MINIGAME.md`).
- **One build, several modes** (`PartyMode`, started by `PartyNet`): `OnlineClient` (UTP WebSocket through `WssBridge`, which exists because stock UTP's handshake gets a 403 from Cloudflare), `DedicatedServer` (`-party-server …`, run by the room service, one Unity process per room), `LocalHost`/`LocalClient` (UDP 7777) and `Practice`. `Bootstrap` in `SP_Boot` reads the command line (`-party-server`, `-autopilot`, else the menu).
- **Authority:** a player's own movement is owner-authoritative (`CritterMotor`, `CritterNetworkTransform`), with a server `SpeedCheck`. Everything that changes the outcome (hits, knockback, mass, elimination, scores, lobby state) is decided on the server. Clients send intents (`FireRpc`, `SessionManager.Request*`), never results.
- **Session:** `SessionFlow` is the rules as plain C# (no Unity, tested on a fake clock); `SessionManager` runs it on the server and mirrors it into network variables. Phases: Lobby → Loading → Intro → Countdown → Playing → RoundResults → Standings → (next game or) Final. Round ranking → session points happens only in `ScoreRules.Award`.
- **UI:** `UiRoot` is the single canvas; one `SessionView` per phase. Views only read state and call `SessionManager.Request*`; they never decide rules.
- **Seats are slots 0–3** everywhere. Knockback events carry the round epoch, and owners drop events from older rounds.

## Rules that are easy to break

- **Network rules** (`ARCHITECTURE.md` section 10): set RPC `InvokePermission` explicitly (NGO's default lets any client invoke); a server-owned object identifies the sender from `RpcParams.Receive.SenderClientId`, never from an argument; validate phase, epoch, finite vectors and lengths in every client RPC; rate-limit with `TokenBucket`; player text goes through `NameRules`; no NetworkObjects in scenes (the server spawns everything).
- **Clients and the online server must come from the same commit.** Each build carries a fingerprint of its network prefab ids (`PartyProtocol.Fingerprint`), so any rebuild of core or Knockback assets means the server must be redeployed before new clients go out.
- **Protocol change** (RPCs, network variables, join payload): bump the version in all of `PartyProtocol.Version`, `VERSION` in `rooms/room_service.py`, and the `X-ShooterParty-Version` header in `deploy.sh` and `e2e_local.sh`.
- **Tickets** are signed in Python (`rooms/tickets.py`) and checked in C# (`Net/Ticket.cs`); both test suites share the vectors from `rooms/make_vectors.py`. Change both sides together.
- **The repo is public.** No IPs, host names, user names, keys or tickets in git; use placeholders like `<ssh-host>`. The public game address `partyshooter.ezellm.com` is fine.
